# Техническое задание: интеграционные тесты авторизации, Bluemap-прокси и служебных маршрутов API

## 1. Назначение документа

Документ предназначен для coding-агента, который должен **дописать автоматические тесты** для частей сервера GrieferFinder, не покрытых тестами сегодня:

1. Авторизация через Discord OAuth: `server/src/auth.js`.
2. Прокси Bluemap-тайлов: маршрут `/api/bluemap/...` в `server/src/index.js`.
3. Служебные маршруты и обработка ошибок в `server/src/index.js`.

Это **задача только на тесты**. Код приложения в `server/src/` менять не нужно, кроме случаев, описанных в разделе 9. Если тест обнаруживает настоящую ошибку в коде, агент не исправляет её молча, а фиксирует в отчёте (раздел 10).

### Зачем это нужно

Эти части отвечают за безопасность (вход, роли, чёрный список) и ходят во внешние сервисы (Discord, Bluemap). Если их случайно сломать, об этом узнают пользователи, а не тесты.

## 2. Что уже есть и чего не хватает

Уже покрыто:

- `server/test/query-pipeline.test.js`: интеграционные тесты `/api/query`, `/api/aggregate`, `/api/query-plan` и `/api/event/...` через `app.inject()` на in-memory SQLite со схемой CoreProtect.
- `server/test/auth-db.test.js`: только класс `AuthStore` (одноразовость OAuth state, блокировка пользователя и отзыв сессий).
- `server/test/config-and-filters.test.js` и `server/test/aggregate-cache.test.js`: разбор конфига, фильтры, кеш агрегатов.

**Не покрыто** (предмет этого задания):

- маршруты `registerAuth` (`/api/auth/*`, `/api/admin/blacklist*`) и хук `preHandler`;
- прокси `/api/bluemap/:world/:zoom/:tx/:tz.png`;
- `/api/meta`, `/api/config`, `/api/sync/*`, `/api/meta/refresh`;
- общий обработчик ошибок и поведение 404 для `/api/*` и SPA-фолбэк на `index.html`.

## 3. Термины

- **Integration test** — тест, который вызывает HTTP-маршрут целиком (`app.inject(...)`), а не отдельную функцию.
- **Мок (mock)** — подделка внешнего сервиса. Здесь это `fetchImpl`, который подставляется вместо настоящего `fetch`, чтобы тесты не ходили в Discord или Bluemap.
- **Store** — объект, который вместо базы CoreProtect отдаёт тестовые данные. Уже существует в `query-pipeline.test.js` как функция `store()`.
- **AuthStore** — хранилище сессий и чёрного списка из `server/src/auth-db.js`.

## 4. Технические ограничения

1. Использовать только встроенный раннер `node:test` и `node:assert/strict`. Новые зависимости не добавлять. Запуск: `cd server && npm test`.
2. Стиль файлов: ESM-импорты, одинарные кавычки, точки с запятой, как в существующих тестах.
3. Никаких обращений к реальной сети. Любой `fetch` к Discord и Bluemap идёт только через подставной `fetchImpl`.
4. Тесты независимы друг от друга: у каждого свои `store`, `AuthStore` и приложение. Все ресурсы закрываются в `finally` (`await app.close()`, `store.close()`), как в существующих тестах.
5. Для `AuthStore` использовать временную папку (`fs.mkdtempSync(path.join(os.tmpdir(), 'cpmv-auth-'))`, удалять после теста) или in-memory, как в `auth-db.test.js`. Файлы в репозитории не создавать.
6. Время: если нужно проверять истечение сессий или интервал проверки ролей, управлять временем через параметры конфига (`sessionMaxAgeMs`, `roleCheckIntervalMs`) и данные в `AuthStore`. Реальные `setTimeout` и `sleep` не использовать.
7. `registerAuth` читает `DISCORD_CLIENT_ID` и `DISCORD_CLIENT_SECRET` из `process.env`. Тест должен выставлять их перед созданием приложения и **восстанавливать прежние значения** после (в `finally` или `t.after`).
8. Тесты должны быстро проходить: весь набор из этого задания не дольше нескольких секунд.

## 6. Тесты авторизации: `server/test/auth-routes.test.js`

Общие настройки для файла: `discordAuth.enabled: true`, `publicOrigin: 'http://localhost:3010'`, корректные 17–20-значные Discord ID для `guildId` и `adminRoleId`, один или два `moderatorRoleIds`.

### 6.1. Конфигурация

- При `enabled: true` и отсутствии `DISCORD_CLIENT_ID` или `DISCORD_CLIENT_SECRET` сборка приложения отклоняется с понятным сообщением.
- При `enabled: true` и некорректных `guildId` или `adminRoleId` (не Discord ID) сборка отклоняется.
- При `enabled: false` приложение собирается без секретов.

### 6.2. Режим без авторизации (`enabled: false`)

- `GET /api/auth/me` возвращает локального пользователя с ролью `moderator`.
- `GET /api/auth/discord/start` возвращает `503`.
- Остальные `/api/*` маршруты доступны без cookie.

### 6.3. Начало входа: `GET /api/auth/discord/start`

- Отвечает редиректом на `https://discord.com/oauth2/authorize`.
- В параметрах редиректа есть `response_type=code`, `client_id`, `redirect_uri` из конфига, `scope=identify guilds.members.read`, `state`, `code_challenge` и `code_challenge_method=S256`.
- Устанавливается cookie `cpmv_oauth_state` с флагами `HttpOnly` и `SameSite=Lax`. Значение cookie совпадает с параметром `state` в URL.
- Для `publicOrigin` с `https://` в cookie есть флаг `Secure`, для `http://` его нет.
- Два вызова подряд дают разные `state`.

### 6.4. Завершение входа: `GET /api/auth/discord/callback`

Успешный сценарий (через `fakeDiscord`):

- Корректные `code` и `state` (в query и в cookie совпадают) приводят к редиректу на `publicOrigin`.
- Выставляется cookie `cpmv_session` (`HttpOnly`, `SameSite=Lax`, `Max-Age` соответствует `sessionMaxAgeMs`).
- Сессия появилась в `AuthStore`, и в ней сохранена верная роль.
- Cookie `cpmv_oauth_state` сбрасывается (`Max-Age=0`).
- На вызов `.../oauth2/token` отправлены `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `client_secret` и `code_verifier`. Значение `code_verifier` совпадает с тем, что было сохранено при `start`.
- Роль определяется правильно: `adminRoleId` даёт `admin`, одна из `moderatorRoleIds` даёт `moderator`. Если в гильдии есть и роль админа, и роль модератора, результат `admin`.

Отказы:

- Нет `code`, нет `state`, нет cookie, `state` не совпадает с cookie: `400 invalid oauth state`.
- `state` использован повторно (повтор того же запроса): `400`.
- `state`, срок которого истёк: `400`.
- У пользователя нет ни одной нужной роли: редирект на `<publicOrigin>/?auth=denied`, сессия **не** создаётся, cookie `cpmv_session` не выставляется.
- Пользователь в чёрном списке: тот же редирект с `?auth=denied`.
- Discord отвечает `401`: сервер отвечает ошибкой 401 и не падает.
- Discord отвечает `429` или `500`: сервер отвечает `503`.

### 6.5. Текущий пользователь и выход

- `GET /api/auth/me` без cookie: `401`. С валидной сессией: `200` с полями `id`, `username`, `avatar`, `role`. Ответ **не содержит** `access_token`, `refresh_token` и других секретов.
- Cookie с несуществующим токеном или токен просроченной сессии: `401`.
- После `POST /api/auth/logout`: `204`, cookie сброшена, сессия удалена из `AuthStore`, а повторный `GET /api/auth/me` с тем же токеном даёт `401`.
- Выход без cookie тоже даёт `204` и не падает.

### 6.6. Повторная проверка ролей (`roleCheckIntervalMs`)

Через `AuthStore.createSession` создать сессию с `rolesCheckedAt` в далёком прошлом. Тогда при обращении к API сервер должен обратиться в Discord за ролями:

- Роль сохранилась: запрос проходит, `roles_checked_at` обновлён.
- Роль пропала (список ролей пуст): сессия удалена, ответ `401`.
- Пользователя внесли в чёрный список между проверками: сессия удалена, `401`.
- Токен доступа истёк, а `refresh_token` есть: сервер запрашивает новый токен (`grant_type=refresh_token`), обновляет данные сессии и проверяет роли.
- Токен истёк, а `refresh_token` нет: сессия удалена, `401`.
- Discord отвечает `429` или `500` во время проверки: ответ `503`, сессия **не** удаляется (временный сбой не должен выкидывать пользователя).
- Если интервал проверки ещё не прошёл, запросов в Discord быть не должно (проверить по списку вызовов мока).

### 6.7. Защита маршрутов (хук `preHandler`)

При `enabled: true`:

- Без сессии `/api/query`, `/api/aggregate`, `/api/meta`, `/api/config`, `/api/bluemap/...` возвращают `401`.
- С валидной сессией те же маршруты доступны.
- `/api/auth/*` и `/api/admin/*` не требуют общего `preHandler`: у них своя проверка.
- Запрос методом `POST`, `PUT`, `PATCH` или `DELETE` с заголовком `Origin`, отличным от `publicOrigin`, получает `403 invalid origin`. С верным `Origin` или без заголовка проходит дальше.
- Для `GET` проверка `Origin` не применяется.

### 6.8. Чёрный список: `/api/admin/blacklist`

- Без сессии: `401`. С ролью `moderator`: `403`. С ролью `admin`: доступ есть.
- `GET` возвращает список (`{ users: [...] }`).
- `POST` с корректным `discordId`: `201`, пользователь в списке. Если у него были сессии, они отозваны.
- `POST` с некорректным `discordId` (не 17–20 цифр, пустое тело, нечисловое значение): `400`.
- `DELETE /api/admin/blacklist/:discordId` возвращает `{ removed: true }` для существующего и `{ removed: false }` для отсутствующего.
- Админ не может «случайно выбить» чужую сессию без блокировки: отзыв делается только через `block`.
- Модератор, заблокированный админом, при следующем запросе получает `401`, даже если cookie ещё действует.

### 6.9. Cookie

- Разбор cookie не падает на мусорных значениях (пустой заголовок, значение без `=`, лишние пробелы, символы с процентным кодированием).
- Некорректное процентное кодирование (`%E0%A4%A`) не должно приводить к ответу `500`. Если сейчас приводит, не чинить, а описать в отчёте как найденную проблему и пометить тест `{ todo: true }` с поясняющим комментарием.

## 7. Тесты Bluemap-прокси: `server/test/bluemap-proxy.test.js`

Прокси находится в `index.js`: `GET /api/bluemap/:world/:zoom/:tx/:tz.png`. Он обращается к `<baseUrl>/maps/<world>/tiles/<zoom>/x<tx>/z<tz>.png`.

Для всех сценариев использовать `fetchImpl`-мок, который записывает URL. Авторизацию отключить (`discordAuth.enabled: false`), кроме одного сценария из 7.5.

### 7.1. Успех

- Ответ `200`, тело совпадает с байтами из мока.
- `Content-Type` берётся из ответа апстрима, а если его нет, то подставляется `image/png`.
- `Cache-Control: public, max-age=300`.
- Мок получил ровно такой URL, как ожидается из `baseUrl`, мира, зума и координат. Если у `baseUrl` есть завершающий `/`, двойного слеша в URL быть не должно.

### 7.2. Отключено или не настроено

- `bluemap.enabled: false`: `404` с `{ error: 'bluemap disabled' }`, мок **не вызывается**.
- `enabled: true`, но пустой `baseUrl`: то же самое.
- Нет блока `bluemap` в конфиге вообще: то же самое.

### 7.3. Ошибки апстрима

- Апстрим вернул `404`: прокси возвращает `404`.
- Апстрим вернул `500`: прокси возвращает `500` с понятным `error`.
- `fetchImpl` бросает исключение (сеть недоступна). Зафиксировать **текущее** поведение: ожидается ответ `500` без утечки текста исключения и стека в тело ответа (см. обработчик ошибок). Тест не должен падать процессом.

### 7.4. Безопасность параметров

Проверить, что значения из пути экранируются и не позволяют выйти за пределы ожидаемого адреса:

- В `world` или `zoom` попадает `..%2F..%2Fsecret` или похожее значение: итоговый URL, который получил мок, содержит экранированные символы (`%2F`, `%2E`), а не слеши, и по-прежнему начинается с `<baseUrl>/maps/`.
- Значение, содержащее `?` или `#` (после кодирования), не добавляет query-часть или фрагмент к адресу апстрима.
- Прокси всегда обращается только к `baseUrl` из конфига, а не к адресу из запроса.

Если выясняется, что часть таких сценариев ведёт к обращению к чужому адресу, не чинить код, а оформить это как найденную проблему (раздел 10) и пометить соответствующий тест `todo`.

### 7.5. Авторизация

При `discordAuth.enabled: true` запрос к `/api/bluemap/...` без сессии получает `401` и **не вызывает** апстрим.

## 8. Тесты служебных маршрутов: `server/test/service-routes.test.js`

Авторизация отключена, если не сказано иначе.

### 8.1. `/api/config`

- Возвращает `bluemap`, `defaultLimit`, `materialNamePrefixesToStrip` и `coreProtectTiles` (с нормализованными значениями).
- Не отдаёт чувствительных данных: нет `databasePath`, `discordAuth`, секретов, `cachePath`. Проверить ключи ответа явно.
- При отсутствии `bluemap` в конфиге: `bluemap: { enabled: false }`.

### 8.2. `/api/meta` и `/api/meta/refresh`

- Успех: возвращает объект метаданных. Структуру брать из того, что отдаёт тестовый store.
- Если `store.getMeta` бросает исключение: `/api/meta` отвечает `503` с `{ error: 'db not ready' }`.
- `POST /api/meta/refresh`: успех возвращает метаданные, а при исключении ответ `500` с `{ error: 'metadata refresh failed' }`.
- Проверить и зафиксировать в комментарии теста, что в ответе об ошибке **не** должно быть стека. Если поле `detail` с текстом исключения сейчас отдаётся клиенту, зафиксировать как наблюдение (раздел 10).

### 8.3. `/api/sync/status` и `/api/sync/start`

- `GET /api/sync/status` возвращает `store.status`.
- `POST /api/sync/start` вызывает `refreshMeta`. При исключении возвращает статус, в котором поле `error` заполнено, и не падает.

### 8.4. Обработчик ошибок

Подключить к тестовому store метод, бросающий ошибку с разными кодами, и проверить:

- ошибка клиента (`statusCode` 4xx) возвращается как есть со своим сообщением (пример: `/api/query?cursor=nope` даёт `400`);
- неожиданная ошибка даёт `500` с телом `{ error: 'internal server error' }`, без стека и без текста исключения;
- ошибка с `statusCode` 5xx приводится к `500`.

### 8.5. Неизвестные маршруты и статика

Создать временный `rootDir` с каталогом `web/dist/index.html` и записать туда уникальную строку:

- `GET /не-существующая-страница` возвращает содержимое `index.html` (SPA-фолбэк);
- `GET /api/не-существует` возвращает `404` с `{ error: 'not found' }` в JSON, а не `index.html`;
- `GET /` отдаёт `index.html`.

Если `web/dist` отсутствует (как в существующих тестах: `rootDir: 'no-static-test-root'`), приложение собирается и API работает.

### 8.6. CORS

- При `enabled: false` заголовок `Access-Control-Allow-Origin` равен `*`.
- При `enabled: true` и `Origin`, равном `publicOrigin`, заголовок равен этому `Origin`, плюс `Vary: Origin`.
- При `enabled: true` и чужом `Origin` заголовка `Access-Control-Allow-Origin` нет.
- `OPTIONS`-запрос отвечает без тела и не требует сессии.

Если по этому пункту поведение отличается от ожидаемого, зафиксировать в отчёте.

## 9. Допустимые изменения в коде приложения

В `server/src/` вносить изменения можно **только если без них нельзя написать тест**, и только минимальные:

- экспортировать уже существующую внутреннюю функцию;
- добавить необязательный параметр (с прежним значением по умолчанию), чтобы подставить мок.

Любое такое изменение:

1. не должно менять поведение приложения;
2. описывается в отчёте отдельным пунктом с причиной.

Ошибки и сомнительные места исправлять **нельзя**: только фиксировать (раздел 10).

## 10. Что должен вернуть агент (отчёт)

После работы агент пишет краткий отчёт на русском языке:

1. **Что добавлено.** Список файлов и количество тестов в каждом.
2. **Результат запуска.** Вывод `cd server && npm test`: сколько тестов прошло, упало, помечено `todo`. Старые тесты по-прежнему проходят.
3. **Найденные проблемы в коде.** Для каждой: где (`файл:строка`), как воспроизвести, чем опасно, что предлагается. Только описание, без исправления. Особое внимание:
   - ответ на сбой `fetchImpl` в Bluemap-прокси (нет `try/catch`);
   - разбор cookie с некорректным процентным кодированием;
   - поле `detail` в ответе `/api/meta/refresh`;
   - поведение CORS при чужом `Origin`.
4. **Изменения в `server/src/`**, если были (раздел 9).
5. **Что не удалось покрыть и почему.**

## 11. Критерии приёмки

1. `cd server && npm test` завершается без ошибок. Тесты, помеченные `todo` для найденных проблем, допускаются, если они описаны в отчёте.
2. Сеть тестами не используется: можно запускать офлайн.
3. После запуска не остаётся временных файлов и открытых соединений. Процесс `node --test` завершается сам, без зависания.
