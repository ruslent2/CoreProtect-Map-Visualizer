# Техническое задание: ручное обновление данных и tiled renderer

## 1. Назначение документа

Документ предназначен для нового coding-агента, который должен переработать загрузку и отображение CoreProtect-данных в проекте `CoreProtect-Map-Visualizer`.

Главный пользовательский сценарий: модератор выбирает игрока и период (например, последние 24 часа) и должен сразу увидеть **все затронутые участки мира**, включая удалённые края карты. После общего обзора приложение постепенно загружает подробные события, начиная с области около зафиксированного центра камеры.

Работать следует с текущей архитектурой проекта и не переписывать приложение без необходимости.

## 2. Подтверждённые решения пользователя

1. CoreProtect-данные обновляются **только вручную**:
   - кнопкой `Обновить данные`;
   - сочетанием `Ctrl+Enter` (`Cmd+Enter` на macOS).
2. До первого обновления слой CoreProtect пуст. BlueMap и UI могут загружаться автоматически.
3. После изменения камеры или фильтров предыдущий результат остаётся видимым, но интерфейс показывает наличие неприменённых изменений.
4. Временной фильтр содержит точные поля начала и окончания и быстрые пресеты:
   - `6ч`;
   - `24ч`;
   - `7д`;
   - `30д`;
   - `Всё время`.
5. Если пользователь явно не выбрал временной режим, при обновлении применяется диапазон последних 6 часов независимо от остальных фильтров.
6. Явный выбор `Всё время` отменяет автоматические 6 часов.
7. Если задано начало, но конец пуст, конец фиксируется текущим временем в момент ручного обновления.
8. Пользовательский glob-фильтр `!#*` установлен по умолчанию, реально отправляется в SQL и исключает CoreProtect-акторов, начинающихся с `#`.
9. `!#*` не считается содержательным фильтром при анализе состояния UI. Список таких служебных значений должен расширяться в коде.
10. Для первой реализации используется **tiled Canvas renderer**, а PixiJS загружает маленькие Canvas как WebGL-текстуры.
11. Если результатов больше `defaultLimit`, сначала отображается обзор **всех занятых Minecraft-чанков**, после чего подробные spatial tiles загружаются от стартового центра камеры до ручной остановки.
12. Порядок очереди фиксируется по центру камеры в момент нажатия `Обновить данные`. Последующий pan/zoom не пересортировывает очередь.
13. Клик по агрегированному чанку или tile поднимает соответствующий spatial tile в начало очереди детализации.
14. После общего обзора камера не перемещается автоматически. Добавляется кнопка `Показать все результаты`.
15. При тяжёлом точном `COUNT(*)` разрешён capped-count: достаточно быстро установить факт `> defaultLimit`; точное количество может быть уточнено агрегацией или в ходе загрузки.
16. Размер transport tile и параллельность загрузки задаются в `config.json`.
17. Сейчас в коде установлена старая дата, последнего обновления базы данных. 

## 3. Термины

Во избежание путаницы использовать разные названия:

- **Minecraft chunk** — область `16×16` блоков. Применяется для агрегированного обзора.
- **Transport tile / spatial tile** — крупная область, по умолчанию `256×256` блоков. Применяется для API-пагинации, небольших текстур и очереди детализации.
- **LOD overview** — агрегированное отображение Minecraft-чанков.
- **Detail tile** — transport tile с отдельными CoreProtect-событиями.
- **Draft filters** — значения, редактируемые в UI.
- **Applied request** — неизменяемый снимок фильтров, времени, камеры и конфигурации, созданный при ручном обновлении.

Не делать один HTTP-запрос на каждый Minecraft-чанк. Это создаст недопустимое количество запросов. Запрашивать данные крупными transport tiles, а внутри агрегировать или рисовать Minecraft-чанки.

## 5. Конфигурация

### 5.1. Новый раздел

Добавить в `config.json` и `config.example.json`:

```json
{
  "defaultLimit": 50000,
  "coreProtectTiles": {
    "tileSize": 256,
    "maxConcurrentRequests": 2,
    "detailPageSize": 5000,
    "maxTextureSize": 512
  }
}
```

Названия можно скорректировать только при сохранении ясного разделения с существующим `bluemap.lodFactor`.

### 5.2. Валидация и значения по умолчанию

Backend нормализует конфигурацию:

- `defaultLimit`: целое `1..200000`;
- `tileSize`: целое `16..2048`, кратное 16;
- `maxConcurrentRequests`: целое `1..4`;
- `detailPageSize`: целое `100..20000`, не больше серверного предела;
- `maxTextureSize`: целое, не меньше `tileSize` для режима `1 блок = 1 пиксель` либо используется как ограничение внутреннего разбиения.

`GET /api/config` возвращает нормализованные `defaultLimit`, `coreProtectTiles` и существующий `bluemap`.

Frontend не должен иметь независимый hardcoded `50000` как источник истины. Значение `Filters.limit` и порог стратегии инициализируются из `/api/config`.

Настройку `coreProtectLod.enabled` не создавать.

## 6. Временные фильтры

### 6.1. Состояние

Добавить явный режим времени, чтобы различать отсутствие выбора и осознанное `Всё время`:

```ts
type TimeSelectionMode = 'default' | 'range' | 'all';
```

Рекомендуемая структура:

```ts
interface TimeSelection {
  mode: TimeSelectionMode;
  from: number | null;
  to: number | null;
}
```

Можно хранить это отдельно от транспортного `Filters`, но нельзя определять intent только через `tFrom === null && tTo === null`.

### 6.2. Правила вычисления effective time

При `applyAndRefresh()` создать фиксированный диапазон:

- `mode === 'default'`: `to = now`, `from = now - 6 часов`;
- `mode === 'all'`: `from = null`, `to = null`;
- `mode === 'range'`:
  - если заполнены обе даты — использовать обе;
  - если заполнено только начало — `to = now`;
  - если заполнен только конец — разрешить открытый диапазон `from = null`, `to = выбранное значение`;
  - если начало позже конца — не запускать запрос и показать ошибку.

Время `now` фиксируется один раз на весь applied request. Последовательные страницы не должны расширять верхнюю границу в процессе загрузки.

### 6.3. Интерфейс

В `web/src/ui.ts` добавить:

- `<input type="datetime-local" step="1">` для начала;
- `<input type="datetime-local" step="1">` для конца;
- кнопки пресетов `6ч`, `24ч`, `7д`, `30д`, `Всё время`;
- визуальное выделение активного пресета/режима;
- сообщение об ошибке диапазона.

Пресеты вычисляются от `Date.now()` в момент нажатия. Не использовать `toISOString().slice(...)` напрямую для `datetime-local`, так как это UTC. Реализовать и протестировать helpers:

- epoch seconds → локальная строка `YYYY-MM-DDTHH:mm:ss`;
- локальная строка → epoch seconds.

Удалить фиксированную тестовую дату, если она ещё присутствует в UI.

```ts
const NON_MEANINGFUL_FILTER_VALUES = {
  users: new Set(['!#*']),
```

Добавить чистые функции:


Требования:

## 8. Только ручное обновление CoreProtect-данных

### 8.1. Запрещённые автоматические запросы

После переработки следующие действия не должны вызывать `/api/query`, `/api/aggregate` или новый query-plan endpoint:

- запуск страницы;
- изменение любого фильтра;
- изменение времени;
- выбор мира;
- pan;
- zoom;
- resize;
- выделение bbox правой кнопкой.

Автоматические `/api/config`, `/api/meta` и загрузка BlueMap разрешены.

### 8.2. Draft и applied state

В `web/src/main.ts` разделить состояние:

```ts
let draftFilters: Filters;
let appliedRequest: AppliedRequest | null;
```

`AppliedRequest` должен содержать immutable snapshot:

- clone фильтров;
- effective `tFrom/tTo`;
- мир;
- bbox;
- центр камеры на момент запуска;
- scale на момент запуска;
- `defaultLimit`;
- tile config;
- generation ID;
- snapshot backend, если он реализован.

`onFiltersChanged()` только меняет draft, перестраивает UI и устанавливает `dirty = true`.

`onCamera()`:

- обновляет HUD;
- обновляет BlueMap;
- не делает CoreProtect-запрос;
- может отмечать камеру как изменённую, но уже запущенная очередь остаётся привязана к стартовому центру.

### 8.3. Кнопка и клавиатура

Добавить кнопку `Обновить данные`.

Глобальный обработчик:

```ts
if ((event.ctrlKey || event.metaKey) && event.key === 'Enter')
```

Обычный Enter не перехватывать, потому что он нужен в многострочных glob-полях.

Состояния UI:

- начальное: `Нажмите «Обновить данные»`;
- dirty: `Есть неприменённые изменения · Ctrl+Enter`;
- planning: `Проверка объёма данных…`;
- overview: `Построение обзора…`;
- loading: прогресс детализации и кнопка `Остановить`;
- stopped: частичные данные сохранены;
- error: предыдущая карта сохранена, если новый scan не успел начать commit;
- partial error: загруженные tiles остаются, явно показать неполноту.

При новом ручном обновлении отменять клиентский pipeline предыдущего запроса.

## 9. Стратегия определения объёма

### 9.1. Не выполнять безусловный дорогой COUNT

Требуется быстро определить одну из стратегий:

```ts
'all' | 'overview-and-detail'
```

Предпочтительный первый запрос выбирает максимум `defaultLimit + 1` идентификаторов/строк по текущим фильтрам и snapshot:

- если получено `<= defaultLimit`, полный набор помещается в лимит;
- если получено `defaultLimit + 1`, известно, что набор больше порога, без обязательного полного `COUNT(*)`.

Не считать `rows.length === defaultLimit` доказательством truncation. Для этого нужна дополнительная строка.

### 9.2. Результат plan endpoint

Добавить endpoint, например:

```http
GET /api/query-plan?<filters>
```

Минимальный ответ:

```ts
interface QueryPlanResult {
  strategy: 'all' | 'overview-and-detail';
  threshold: number;
  countAtLeast: number;
  totalExact: boolean;
  total?: number;
  bounds: BBox | null;
  snapshot: SourceSnapshot;
  elapsedMs: number;
}
```

Для capped-результата `countAtLeast = defaultLimit + 1`, `totalExact = false`.

Если вычисление bounds требует полного сканирования и делает capped-plan бессмысленным, bounds разрешается вернуть позднее вместе с агрегированным обзором.

### 9.3. Snapshot

CoreProtect DB изменяется во время чтения. Зафиксировать верхнюю границу отдельно для каждой таблицы:

```ts
interface SourceSnapshot {
  blockMaxRowid: number;
  containerMaxRowid: number;
  itemMaxRowid: number;
}
```

Все страницы и агрегаты applied request должны добавлять соответствующее `rowid <= maxRowid`.

Это не защищает от удаления старых строк внешним процессом, поэтому клиент дополнительно:

- дедуплицирует события по `${src}:${rowid_src}`;
- показывает предупреждение, если итоговые значения не совпадают с полученной сводкой.

## 10. Стратегия `all`: результатов не больше defaultLimit

Если набор помещается в `defaultLimit`:

1. Получить все события applied request по snapshot.
2. Не ограничивать запрос текущим viewport.
3. Разложить события по transport tiles размером `tileSize`.
4. Создать отдельную Canvas/WebGL-текстуру для каждого занятого tile.
5. Рассчитать общий bbox всех событий.
6. Показать кнопку `Показать все результаты`, вызывающую `map.fitTo(bounds)` только по нажатию.
7. Не выделять память для пустого пространства между удалёнными событиями.

Даже при 50 000 событиях нельзя создавать один Canvas по общему bbox мира.

Если безопаснее получать данные страницами, использовать cursor pagination и инкрементально собирать tiles, но визуально результат считается одним applied generation.

## 11. Стратегия `overview-and-detail`: результатов больше defaultLimit

### 11.1. Полный обзор географии

Сначала запросить агрегаты **всех занятых Minecraft-чанков по всему applied filter**, а не только viewport.

Агрегат чанка должен включать минимум:

```ts
interface Chunk {
  cx: number;
  cz: number;
  cnt: number;
  users: number;
  tMin: number;
  tMax: number;
  dominant: ...;
}
```

Из агрегатов получить:

- полный bbox результатов;
- список занятых transport tiles;
- точное или уточнённое количество через сумму `cnt`, если семантика SQL исключает двойной подсчёт;
- обзор всех мест активности, включая края мира.

Обзор отображается сразу tiled renderer-ом. Не создавать текстуру на весь bbox.

Если число агрегированных чанков само слишком велико, endpoint должен поддерживать потоковую/страничную отдачу либо группировку первого уровня по transport tiles с последующей загрузкой chunk-агрегатов. Нельзя возвращать неограниченный гигантский JSON без оценки размера.

### 11.2. Очередь detail tiles

После получения списка только **занятых** transport tiles:

1. Определить transport tile стартового центра:
   - `tx = Math.floor(cameraX / tileSize)`;
   - `tz = Math.floor(cameraZ / tileSize)`.
2. Отсортировать занятые tiles по квадратному расстоянию/кольцам от стартового tile.
3. Зафиксировать порядок на весь applied request.
4. Не отправлять запросы к пустым tiles.
5. Загружать до `maxConcurrentRequests` tiles одновременно.
6. Внутри плотного tile использовать cursor pagination, пока `hasMore === false`.
7. После загрузки detail tile заменить/перекрыть соответствующую агрегированную часть подробным слоем.
8. Продолжать до завершения, нового Apply или нажатия `Остановить`.

Это пользовательски выглядит как спираль от камеры, но не тратит SQL/HTTP на пустое пространство.

### 11.3. Приоритет по клику

При клике по агрегированному Minecraft-чанку:

- определить его transport tile;
- если tile ещё не загружен и не выполняется, переместить его в начало очереди;
- не перестраивать query-plan и не менять applied filters;
- показать в status bar, что область поставлена в приоритет;
- повторный клик не должен дублировать запрос.

### 11.4. Движение камеры во время загрузки

Pan/zoom:

- не пересортировывает очередь;
- не запускает запрос;
- не меняет applied center;
- обновляет только визуальную камеру, HUD и BlueMap.

Новая географическая приоритизация выполняется только новым `Ctrl+Enter`/кнопкой либо явным кликом по чанку.

## 12. Cursor pagination

Расширить `/api/query` или добавить отдельный tile endpoint:

```http
GET /api/query?...&pageSize=5000&cursor=...&snapshot=...&x1=...&x2=...&z1=...&z2=...
```

Ответ:

```ts
interface QueryPageResult {
  events: CpEvent[];
  count: number;
  hasMore: boolean;
  nextCursor: string | null;
  elapsedMs: number;
}
```

Требования:

- стабильный порядок: `ORDER BY time DESC, source_rank ASC, rowid_src DESC`;
- keyset pagination, не `OFFSET`;
- cursor включает `time`, `sourceRank`, `rowid`;
- выбирать `pageSize + 1`, лишнюю строку использовать для `hasMore`;
- snapshot применяется к каждой таблице;
- tile-границы полуоткрытые:

```sql
x >= @xMin AND x < @xMaxExclusive
AND z >= @zMin AND z < @zMaxExclusive
```

Это исключает дубли на границах соседних tiles.

Нормализовать `limit/pageSize`: конечное целое число в допустимом диапазоне. Закрыть существующий обход через `limit=-1`.

## 13. Tiled renderer

### 13.1. Общая архитектура

PixiJS/WebGL остаётся основным renderer. Canvas используется только для подготовки небольших tile-текстур:

```text
API events/chunks
  → CPU rasterization в Canvas tile
  → Pixi Texture
  → WebGL Sprite
```

В `web/src/map.ts` заменить один `pointsSprite` коллекциями:

```ts
Map<TileKey, EventTileRenderState>
Map<TileKey, AggregateTileRenderState>
```

Рекомендуемый интерфейс:

```ts
beginDataGeneration(generation: number): void;
setEventTile(generation: number, tileKey: string, events: CpEvent[], ctx: ColorContext): void;
setAggregateTile(generation: number, tileKey: string, chunks: Chunk[], ctx: ColorContext): void;
removeEventTile(tileKey: string): void;
commitDataGeneration(generation: number): void;
cancelDataGeneration(generation: number): void;
clearData(): void;
fitToResults(): void;
```

Имена могут отличаться, но generation safety и раздельные aggregate/detail layers обязательны.

### 13.2. Размер и координаты

Для tile `(tx, tz)`:

```text
originX = tx * tileSize
originZ = tz * tileSize
localX = event.x - originX
localZ = event.z - originZ
```

Canvas не должен превышать безопасный `maxTextureSize`. При `tileSize > maxTextureSize` tile внутренне разбить на subtiles или запретить такую конфигурацию.

Отрицательные координаты обрабатывать через `Math.floor`, не через truncation.

### 13.3. Слои

Внутри `MapView.world` использовать порядок:

1. BlueMap;
2. aggregate CoreProtect layer;
3. detail CoreProtect layer;
4. selection/interaction overlays.

Когда detail tile готов, агрегаты соответствующей области можно скрыть либо оставить под ним с гарантированным визуальным приоритетом detail.

### 13.4. Индекс hover/click

Не хранить один неуправляемый глобальный индекс без возможности удаления tile.

Для каждого detail tile хранить:

- sprite/texture;
- события;
- локальный `gridIndex` либо список добавленных глобальных ключей;
- множество event IDs для дедупликации.

При замене или удалении tile очистить его hit-index. ID события: `${src}:${rowid_src}`.

Hover и inspector доступны только для загруженных detail tiles. Для агрегированного чанка hover показывает сводку и предлагает кликнуть для приоритетной детализации.

### 13.5. Ограничения памяти

Первая версия загружает detail tiles до ручной остановки, как выбрал пользователь. Тем не менее агент обязан:

- уничтожать заменённые Pixi texture/textureSource;
- не хранить дубликаты событий;
- не создавать Canvas `16384×16384`;
- отображать количество загруженных событий и tiles;
- дать пользователю остановить pipeline;
- оценить память и документировать риск при миллионах событий.

Не вводить скрытое удаление уже загруженных результатов без отдельного согласования. Если браузер приближается к техническому пределу, остановить детализацию с понятным предупреждением, сохранив агрегированный обзор.

### 13.6. Будущая замена renderer

Не связывать API/очередь напрямую с Canvas. Выделить интерфейс rasterizer/tile renderer так, чтобы позднее можно было заменить Canvas tiles на Pixi custom geometry/WebGL point buffers без изменения backend-контрактов и scan pipeline.

WebGPU в рамках этого ТЗ не внедрять.

## 14. Камера

Исправить существующий callback камеры независимо от ручной загрузки:

- `updateTransform()` может оставаться в Pixi ticker, но должен сравнивать `cx`, `cz`, `scale`, renderer width/height с последним применённым состоянием;
- `onCameraChange` вызывается только при реальном изменении;
- CoreProtect refresh из callback удалить полностью;
- HUD и BlueMap обновляются при реальном изменении;
- resize учитывается;
- zoom использует фактический коэффициент после clamp, чтобы камера не прыгала на `MIN_SCALE/MAX_SCALE`.

LOD не должен сам запускать SQL. Переключение visual mode после zoom допускается только для уже загруженных данных; если требуются новые данные, показать dirty/недоступность до ручной команды.

## 15. Смена мира и BlueMap

При изменении draft world:

- вызвать `bluemap.setWorld(draftFilters.world)` для визуальной подложки;
- обновить HUD безопасным DOM API;
- CoreProtect-слой не обновлять автоматически;
- старые applied CoreProtect-данные оставить с явным индикатором, что они относятся к предыдущему applied world;
- после ручного Apply заменить их новым generation.

После получения `/api/meta` нормализовать начальный мир: если `world` отсутствует, выбрать первый доступный, а не продолжать использовать несуществующий hardcoded `world`.

## 16. Отмена, поколения и гонки

В `web/src/api.ts` все новые методы принимают `AbortSignal`.

В `web/src/main.ts`:

```ts
let generation = 0;
let activeController: AbortController | null = null;
```

При новом Apply:

1. abort предыдущего клиента;
2. увеличить generation;
3. создать controller;
4. зафиксировать AppliedRequest;
5. перед каждым изменением карты/status проверять generation.

Важно: abort браузерного fetch не прерывает уже выполняющийся синхронный SQL `better-sqlite3`. Поэтому серверная параллельность должна быть низкой, а устаревший результат запрещено применять.

При `Остановить`:

- остановить выдачу новых tile-запросов;
- abort активных fetch;
- оставить уже загруженные tiles и полный aggregate overview;
- status показывает частичный результат.

## 17. Backend: переиспользование фильтров

В `server/src/queries.js` не дублировать SQL-семантику между count, plan, aggregate и detail.

Выделить переиспользуемые части:

- `parseFilters()`;
- строгую числовую валидацию;
- разрешение glob-паттернов;
- построение table plans;
- snapshot conditions;
- spatial conditions.

Все стратегии должны одинаково учитывать:

- world;
- effective time;
- bbox пользователя;
- users и `!#*`;
- actions;
- materials;
- Y;
- snapshot.

Существующие неоднозначности `other/entity_kill` и пересекающихся material/entity ID не исправлять попутно без отдельного тестируемого решения, но count и query не должны расходиться по текущей семантике.

Невалидные числа, обратный bbox и `tFrom > tTo` должны давать HTTP 400, а не тяжёлый или неожиданный SQL.

## 18. Metadata

Перед новым applied scan желательно обновить server metadata, потому что CoreProtect DB живая и могли появиться новые игроки/материалы.

Допустимые варианты:

- вызвать существующий `POST /api/sync/start`, затем `/api/meta`;
- предпочтительно добавить честный `/api/meta/refresh`, сохранив старый endpoint для совместимости.

Не показывать фиктивный sync progress: текущий `sync/status.running` не отражает копирование событий.

Ошибка обновления metadata не должна молча превращать фильтр нового игрока в пустую выборку. Показать понятную ошибку или предупреждение.

## 19. UX общего обзора

После aggregate overview показать:

- найдено не менее/точно N событий;
- число занятых Minecraft-чанков;
- число занятых transport tiles;
- общий временной диапазон;
- прогресс detail tiles;
- кнопки:
  - `Показать все результаты`;
  - `Остановить`;
  - при необходимости `Повторить пропущенные`.

Примеры статусов:

```text
Найдено больше 50 000 событий · построение обзора…
83 412 событий · 1 286 чанков · 46 областей
Загружено детально 18 430 / 83 412 · 12 / 46 областей
Остановлено: обзор полный, детализация 18 430 / 83 412
Частичные данные: ошибка области 12,-4
```

Если `totalExact === false`, не показывать приблизительное число как точное. Использовать `> 50 000` или `не менее 50 001` до уточнения.

## 20. Ошибки и атомарность отображения

- Ошибка plan до начала новой generation: сохранить старую карту.
- Ошибка общего overview: сохранить старую карту и сообщить, что обновление не применено.
- После успешного overview можно переключить карту на новый generation.
- Ошибка одного detail tile: общий обзор и другие tiles сохраняются; tile помечается для retry.
- Не позволять старому ответу перезаписать новый generation.
- При изменении DB во время scan показать предупреждение, а не скрывать расхождение.

## 21. Производительность

Перед финализацией выполнить на **копии** реальной БД:

- `EXPLAIN QUERY PLAN` для мира + 6ч;
- мира + 24ч + игрок;
- мира + `!#*`;
- action/material filters;
- capped plan;
- полного chunk overview;
- detail tile `256×256`;
- плотного tile с несколькими cursor pages.

Не создавать индексы в оригинальной CoreProtect DB: соединение read-only.

Учитывать, что `better-sqlite3` блокирует event loop. Если полный aggregate overview занимает неприемлемое время, документировать результаты и предложить worker thread/отдельный read-only процесс, но не менять архитектуру наугад.

Целевые ориентиры, которые нужно проверить, а не считать гарантированными:

- capped plan за обычные 6 часов: до 1–2 секунд;
- detail page: до 0.5–1 секунды;
- не более двух одновременных SQL-запросов;
- отсутствие Canvas/текстур больше заданного безопасного размера.

## 22. Тесты backend

Добавить отдельные тесты, а не перегружать только `aggregate-cache.test.js`:

1. `!#*` исключает `#environment`, но оставляет обычного игрока.
2. Default user-filter реально участвует в SQL.
3. Plan при `total === defaultLimit` выбирает `all`.
4. Plan при `total === defaultLimit + 1` выбирает `overview-and-detail`.
5. Capped plan корректно выставляет `totalExact=false`.
6. Chunk overview учитывает все три source-таблицы.
7. Сумма chunk counts совпадает с полной выборкой на fixture.
8. Count/overview/query используют одинаковые filters и snapshot.
9. Cursor не теряет строки с одинаковым timestamp.
10. Одинаковые rowid разных source не конфликтуют.
11. Новая строка после snapshot не попадает в scan.
12. Соседние transport tiles не дублируют граничные координаты.
13. Отрицательные координаты корректно попадают в tile.
14. Плотный tile дочитывается несколькими страницами.
15. `limit=-1`, `NaN`, Infinity, дробные/обратные диапазоны отклоняются или нормализуются согласно контракту.
16. `hasMore` определяется через дополнительную строку.
17. Aggregate overview не использует устаревший cache.

Production Fastify желательно экспортировать через factory `buildApp({ store, cfg })`, чтобы endpoint-тесты не запускали реальный listener при import.

## 23. Тесты frontend

Добавить Vitest либо эквивалент для чистых helpers:

1. epoch ↔ `datetime-local` в локальной timezone.
2. Пресеты 6ч/24ч/7д/30д.
3. `default` фиксирует последние 6 часов.
4. `all` остаётся всем временем.
5. Начало без конца фиксирует `now`.
6. `!#*` не считается содержательным.
7. `!#*` плюс `Alice` считается содержательным.
8. Служебный allowlist расширяется без изменения основной функции.
9. Раскладка событий по tiles для положительных и отрицательных координат.
10. Tile bbox не перекрываются.
11. Сортировка занятых tiles начинается от applied camera tile и фиксируется.
12. Клик поднимает tile в очередь без дубля.
13. Дедупликация `${src}:${rowid_src}`.
14. Старый generation не изменяет карту/status.
15. Rasterization не создаёт Canvas по общему bbox.
16. Замена detail tile не уничтожает соседние tiles.
17. Удаление tile очищает hover-index и GPU-ресурсы.

## 24. Ручные приёмочные сценарии

### 24.1. Однодневный грифер

1. Открыть приложение.
2. Убедиться, что CoreProtect-запрос автоматически не выполнялся.
3. Выбрать игрока.
4. Выбрать `24ч` или точные даты.
5. Нажать `Обновить данные`.
6. Если событий больше limit, увидеть полный обзор всех занятых чанков, в том числе удалённых краёв мира.
7. Нажать `Показать все результаты` и увидеть все области в viewport.
8. Кликнуть удалённый чанк и убедиться, что его detail tile загружается приоритетно.

### 24.2. Ручной режим

- Изменение фильтра не создаёт CoreProtect-запрос.
- Pan/zoom не создаёт CoreProtect-запрос.
- `Ctrl+Enter` создаёт ровно один новый pipeline.
- Enter в многострочном поле остаётся обычным Enter.
- Старая карта остаётся до успешного применения нового overview/result.

### 24.3. Время

- Без явного выбора применяется ровно шесть часов до момента Apply.
- Повторный Apply позднее фиксирует новый шестичасовой диапазон.
- `Всё время` не заменяется шестью часами.
- Начало без конца получает фиксированный конец `now`.

### 24.4. Большие данные

- `<= defaultLimit`: все события мира отображаются tiled, независимо от viewport.
- `> defaultLimit`: сначала полный chunk overview, затем detail tiles.
- Никаких запросов к заведомо пустым transport tiles.
- `Остановить` сохраняет overview и уже загруженные детали.
- Два далёких события не создают огромную текстуру между ними.

### 24.5. Камера и BlueMap

- Неподвижная камера не вызывает callback 60 раз в секунду.
- Resize корректно обновляет transform и BlueMap.
- Смена мира обновляет BlueMap, но ждёт ручного Apply для CoreProtect.
- Результаты не выполняют автоматический `fitTo`; кнопка делает это явно.

## 26. Критерии готовности

Работа считается завершённой, если одновременно выполняются условия:

- CoreProtect SQL запускается только кнопкой или `Ctrl/Cmd+Enter`;
- default applied time равен последним 6 часам, а явное `Всё время` сохраняется;
- `!#*` включён по умолчанию, работает в SQL и объявлен служебным через расширяемую политику;
- `defaultLimit` и tile-параметры приходят из server config;
- малая выборка отображается полностью по всему миру через tiles;
- большая выборка сначала показывает все занятые Minecraft-чанки, включая края мира;
- детализация идёт только по занятым transport tiles в фиксированном порядке от applied camera center;
- клик приоритизирует область;
- пользователь может остановить загрузку и показать весь bbox результатов;
- отсутствует единый огромный Canvas по bbox мира;
- старые ответы не перезаписывают новый generation;
- pan/zoom не инициирует SQL;
- тесты и `npm.cmd run build:web` проходят.
