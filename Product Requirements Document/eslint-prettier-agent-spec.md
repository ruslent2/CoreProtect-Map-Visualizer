# Техническое задание: внедрение ESLint и Prettier

## 1. Назначение документа

Документ предназначен для coding-агента, который должен подключить к проекту GrieferFinder **автоформатирование (Prettier)** и **проверку кода на типичные ошибки (ESLint)**, а затем единообразно отформатировать весь существующий код.

Цель: код читается легко (нормальные отступы и переносы строк), а типичные ошибки ловятся автоматически до запуска. Задание также закрывает пункт из `todo.md`: «Переписать все файлы в читабельный вид — переносы строк!».

Это задача про **инструменты и оформление**. Логику приложения менять нельзя.

## 2. Что такое ESLint и Prettier (для читающего задание человека)

- **Prettier** — автоформатер. Сам расставляет отступы, переносы строк, кавычки, точки с запятой. Спорить о стиле не нужно: правила задаются один раз.
- **ESLint** — проверка на ошибки. Находит неиспользуемые переменные, подозрительные сравнения, забытый `await` и тому подобное. Стиль он не проверяет: за это отвечает Prettier.
- Они дополняют друг друга и не должны конфликтовать: правила ESLint, касающиеся оформления, отключаются (`eslint-config-prettier`).

## 3. Текущее состояние проекта (проверено)

- Три `package.json`: корневой (без зависимостей, только скрипты-обёртки), `server/` и `web/`. У `server/` и `web/` свои `package-lock.json`. Workspaces нет.
- Сервер: JavaScript (ESM, `"type": "module"`), Node.js, Fastify. Тесты: `node --test` (`server/test/*.test.js`).
- Веб: TypeScript (strict), Vite, Vitest, Pixi.js. Тесты: `web/test/*.test.ts`.
- `web/tsconfig.json` включает только `src` (папка `web/test` проверкой типов не охватывается).
- ESLint, Prettier, `.editorconfig`, `.gitattributes` в проекте нет.
- Фактический стиль: одинарные кавычки (в `main.ts` 171 строка с `'` против 1 с `"`), точки с запятой, отступ 2 пробела.
- Длинные строки больше 120 символов: `web/src/ui.ts` (39 из 555), `web/src/main.ts` (28 из 858), `server/test/query-pipeline.test.js` (20 из 71), `server/src/index.js`, `server/src/auth.js`, `server/src/queries.js`, `web/src/tiles.ts` и другие.
- Внутри `buildApp` в `server/src/index.js` обработчики не имеют отступа, а `server/test/query-pipeline.test.js` написан плотными однострочниками (`try { ... } finally { ... }`). Это и есть основные кандидаты на перенос строк.
- В репозитории используется Windows-окружение (в README есть PowerShell), поэтому важна единая настройка концов строк.
- Комментарии в коде и сообщения журналов написаны по-украински. Их **не переводить и не править**.

## 4. Границы задачи

**Входит:**

1. Prettier для всего кода: `server/**/*.js`, `web/src/**/*.ts`, `web/test/**/*.ts`, конфиги (`*.js`, `*.ts`, `*.json` кроме lock-файлов), `web/index.html`, `web/src/style.css`, а также Markdown-файлы по решению из раздела 8.
2. ESLint для `server/` (JavaScript) и `web/` (TypeScript).
3. Скрипты запуска в корневом `package.json`.
4. `.editorconfig` и `.gitattributes` для единых концов строк.
5. `.git-blame-ignore-revs`.
6. Одноразовое форматирование всей кодовой базы отдельным коммитом.
7. Короткий раздел в `README.md` о том, как запускать проверки.

**Не входит (делать нельзя):**

- менять логику, названия, API, тексты интерфейса, переводы (`web/src/i18n/locales/*.json` форматировать можно, менять ключи и значения нельзя);
- обновлять версии существующих зависимостей;
- настраивать CI, pre-commit-хуки и Docker (это отдельные задачи);
- переписывать тесты по существу (только формат).

## 5. Решения по инструментам

Эти решения принимает не агент. Их нужно выполнить как написано.

### 5.1. Расположение

ESLint и Prettier ставятся **один раз, в корень** проекта как `devDependencies` корневого `package.json`. Конфиги лежат в корне. Подпроекты `server/` и `web/` свои зависимости для этого не получают.

Корневому `package.json` нужен собственный `package-lock.json` (он появится после `npm install`). Его нужно закоммитить.

Скрипт `install:all` в корневом `package.json` должен ставить зависимости и в корне тоже:
`npm install && cd server && npm install && cd ../web && npm install`.

### 5.2. Пакеты (все в devDependencies корня)

- `prettier`
- `eslint` (версия 9 или новее, flat config)
- `@eslint/js`
- `globals`
- `typescript-eslint`
- `eslint-config-prettier`

Версии: последние стабильные на момент работы, совместимые друг с другом и с TypeScript из `web/package.json`. Каждая версия зафиксирована в lock-файле. Для `typescript-eslint` проверить совместимость с версией `typescript` из `web/`. Если нужна другая версия TypeScript, **сообщить об этом в отчёте, но не обновлять** TypeScript в `web/` самовольно.

### 5.3. Настройки Prettier (`.prettierrc.json`)

```json
{
  "printWidth": 120,
  "singleQuote": true,
  "semi": true,
  "trailingComma": "all",
  "tabWidth": 2,
  "useTabs": false,
  "endOfLine": "lf"
}
```

Обоснование: это соответствует тому, как код уже написан (одинарные кавычки, точки с запятой, отступ 2 пробела). Из текущего стиля меняется только перенос слишком длинных строк.

`.prettierignore`: `node_modules`, `web/dist`, `data`, `**/package-lock.json`, `*.db`, `config.json`, `coverage`.

### 5.4. Настройки ESLint (`eslint.config.js` в корне, flat config, ESM)

Общее:

- Игнорировать: `**/node_modules/**`, `web/dist/**`, `data/**`, `coverage/**`.
- В конце конфига подключить `eslint-config-prettier`, чтобы отключить правила оформления.
- `linterOptions.reportUnusedDisableDirectives: "error"`.

Блок для `server/**/*.js`:

- База: `@eslint/js` `recommended`.
- `languageOptions`: `ecmaVersion: 2022`, `sourceType: "module"`, `globals.node`.
- Правила, в дополнение к `recommended`:
  - `eqeqeq`: `["error", "always", { "null": "ignore" }]`;
  - `no-var`: `error`;
  - `prefer-const`: `error`;
  - `no-unused-vars`: `["error", { "argsIgnorePattern": "^_", "varsIgnorePattern": "^_", "caughtErrors": "none" }]`.

Блок для `web/src/**/*.ts` и `web/test/**/*.ts`:

- База: `@eslint/js` `recommended` и `typescript-eslint` `recommended` (**без** режима, требующего информации о типах, `recommendedTypeChecked` не использовать: он медленный и даст много лишнего шума).
- `languageOptions.globals`: `globals.browser`.
- Правила те же, что для сервера, но вместо базового `no-unused-vars` использовать `@typescript-eslint/no-unused-vars` с теми же параметрами.
- `@typescript-eslint/no-explicit-any`: `warn` (не `error`; в коде могут быть существующие `any`).

Блок для тестов (`server/test/**/*.js`, `web/test/**/*.ts`): допустимы небольшие послабления, только если без них проверка падает на существующем коде. Каждое послабление обосновывается комментарием.

Блок для конфигов (`eslint.config.js`, `web/vite.config.ts`, `web/vitest.config.ts`): `globals.node`.

**Принцип выбора строгости:** сначала запустить `eslint` и посмотреть, что находит. Правила `recommended` должны проходить без ошибок после исправлений из раздела 6. Если правило выдаёт десятки замечаний о коде, который работает, **не отключать правило молча**, а действовать по разделу 7.

## 6. Порядок работ и коммиты

Работа делится на строго отдельные коммиты. Смешивать форматирование и содержательные правки в одном коммите нельзя.

### Коммит 1. Инструменты и конфигурация (без изменения кода)

1. Добавить зависимости в корневой `package.json`, сгенерировать корневой `package-lock.json`.
2. Добавить `.prettierrc.json`, `.prettierignore`, `eslint.config.js`, `.editorconfig`, `.gitattributes`.
3. Добавить скрипты в корневой `package.json` (раздел 5.5).
4. **Исходные файлы кода на этом шаге не менять.**

`.editorconfig`:

```
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
indent_style = space
indent_size = 2
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false
```

`.gitattributes`:

```
* text=auto eol=lf
*.png binary
*.jpg binary
*.ico binary
*.db binary
```

### Коммит 2. Форматирование (только оформление)

1. Запустить `npm run format` (Prettier с записью).
2. Проверить, что изменился **только внешний вид**:
   - вся логика прежняя;
   - после форматирования проходят все тесты: `cd server && npm test` и `cd web && npm test`;
   - проходит `cd web && npx tsc --noEmit` и `cd web && npm run build`.
3. Закоммитить одним коммитом с сообщением вида `style: apply prettier formatting`. В этот коммит **ничего другого** не входит.
4. Сразу после него отдельным маленьким коммитом добавить файл `.git-blame-ignore-revs` с полным хэшем коммита форматирования и комментарием. Это нужно, чтобы `git blame` не показывал форматирование как автора каждой строки. Пример содержимого:

```
# style: apply prettier formatting
<полный 40-значный хэш коммита форматирования>
```

В отчёте указать пользователю команду, которая включает этот файл на его машине: `git config blame.ignoreRevsFile .git-blame-ignore-revs`. (GitHub учитывает файл автоматически.)

Автоформатирование не должно менять поведение, но быстро проверить это можно так: до и после форматирования прогнать тесты и убедиться, что их результат идентичен.

### Коммит 3. Исправления, найденные ESLint

1. Запустить `npm run lint`.
2. Исправить замечания, которые **безопасно** исправляются без изменения поведения:
   - неиспользуемые импорты и переменные (удалить);
   - `var` на `const` или `let`;
   - `==` на `===`, если очевидно, что поведение не меняется (проверять каждый случай; с `null` и `undefined` быть осторожным);
   - `prefer-const`.
3. Для всего, что может изменить поведение или требует решения человека, действовать по разделу 7.
4. Прогнать все тесты, `tsc` и `build`.
5. Закоммитить, например: `chore: fix eslint findings`.

### Коммит 4. Документация

Добавить в `README.md` короткий раздел «Качество кода» (по-украински, как остальной README):

- что такое `npm run lint` и `npm run format`;
- как проверить форматирование без записи (`npm run format:check`);
- одна строка про `.git-blame-ignore-revs`.

В `todo.md` отметить пункт «Переписать все файлы в читабельный вид» как выполненный (`- [x]`), **не трогая** остальные пункты.

### 5.5. Скрипты корневого `package.json`

```json
"lint": "eslint .",
"lint:fix": "eslint . --fix",
"format": "prettier --write .",
"format:check": "prettier --check ."
```

Существующие скрипты (`install:all`, `server`, `dev:server`, `dev:web`, `build:web`) не менять, кроме `install:all` (раздел 5.1).

Дополнительно для удобства:

```json
"typecheck": "cd web && tsc --noEmit",
"test": "cd server && npm test && cd ../web && npm test"
```

## 7. Правила обращения с замечаниями, которые нельзя исправить автоматически

Для каждого замечания ESLint, которое:

- может изменить поведение при исправлении (например, `no-fallthrough`, `no-empty`, `no-useless-escape` в регулярных выражениях, `no-prototype-builtins`, `no-cond-assign`, `no-control-regex`, предупреждения про `await` в цикле), или
- указывает на возможную настоящую ошибку (например, забытый `await`, неиспользуемый результат, недостижимый код),

агент **не исправляет код молча**. Он выбирает один из вариантов:

1. Если исправление тривиально и очевидно безопасно, исправить и описать в отчёте.
2. Если спорно, **оставить код как есть** и добавить точечное подавление правила на этой строке в виде `// eslint-disable-next-line <правило> -- <причина>`. Причина обязательна. Общие `/* eslint-disable */` на весь файл и отключение правил в конфиге «ради тишины» запрещены.
3. Все такие места собрать в отчёт списком: файл и строка, правило, что это значит, насколько опасно, что рекомендуется сделать.

Регулярные выражения — особая зона риска: правило `no-useless-escape` и подобные нельзя применять автоматически к фильтрам glob (`*`, `?`, `!`, `(?i)`), которые разбираются в `server/src/queries.js` и `web/src/`. Их менять можно только при полной уверенности, что поведение осталось прежним, и после запуска тестов.

## 8. Что форматировать, а что нет

- **Форматировать:** `*.js`, `*.ts`, `*.json` (кроме lock-файлов), `*.css`, `*.html`.
- **Markdown (`*.md`):** форматировать **нельзя**. В документах есть таблицы и сознательные переносы строк, Prettier может изменить их вид. Добавить `*.md` в `.prettierignore`.
- **`config.example.json`:** форматировать можно, но проверить, что содержимое (значения, порядок ключей) не поменялось.
- **Файлы локализации (`web/src/i18n/locales/*.json`):** форматировать можно. Тест `web/test/i18n.test.ts` должен продолжить проходить. Не менять порядок и значения ключей.
- **`Product Requirements Document/`:** это Markdown, не трогать.

## 9. Критерии приёмки

1. `npm install` в корне и затем `npm run lint` завершается **без ошибок** (предупреждения допустимы и перечислены в отчёте).
2. `npm run format:check` завершается без замечаний.
3. `cd server && npm test` и `cd web && npm test` проходят так же, как до работы. Количество тестов то же.
4. `cd web && npx tsc --noEmit` и `cd web && npm run build` проходят.
5. Приложение запускается: `npm run server` стартует без ошибок (с тестовым `config.json` вне репозитория) либо, если нет базы, хотя бы корректно сообщает об отсутствии конфига так же, как раньше.
6. Ни одна строка логики не изменена в коммите форматирования (проверка: `git diff -w --stat` и выборочный просмотр, плюс прохождение тестов).
7. Нет общих отключений ESLint на уровне файлов и нет отключённых правил в конфиге без пояснения.
8. Существуют отдельные коммиты по разделу 6, а `.git-blame-ignore-revs` содержит верный хэш коммита форматирования.
9. Не добавлены секреты, `config.json`, `*.db`, а также содержимое `node_modules`.
10. В `todo.md` отмечен только соответствующий пункт, остальное не тронуто.

9. Что осталось вне задания (CI, pre-commit-хуки), в одну строку.
