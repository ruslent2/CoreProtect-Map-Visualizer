# Техническое задание: запуск GrieferFinder в Docker

## 1. Назначение документа

Документ предназначен для coding-агента, который должен добавить в проект GrieferFinder `Dockerfile`, `docker-compose.yml` и сопутствующие файлы, чтобы сервер можно было запустить одной командой без ручной установки Node.js и нативной библиотеки `better-sqlite3`.

Задача **осторожная**: контейнер будет читать **живую базу CoreProtect**, в которую в этот момент пишет Minecraft-сервер, и хранить сессии и чёрный список Discord-авторизации. Ошибка в монтировании или правах может сломать чтение, повредить служебные данные или открыть закрытое API в интернет. Поэтому в документе подробно описаны решения и проверки. **Решения из разделов 5–7 выполнять как написано**, а не «как удобнее».

Код приложения (`server/src/`, `web/src/`) менять **нельзя** (подробнее в разделе 4).

## 2. Простыми словами: что такое Docker и зачем он здесь

- **Образ (image)** — «слепок» готового окружения: нужная версия Node, установленные зависимости, собранный фронтенд и код сервера.
- **Контейнер** — запущенный образ. Изнутри выглядит как отдельный маленький компьютер.
- **Dockerfile** — рецепт сборки образа.
- **docker-compose.yml** — описание запуска: какой порт открыть, какие папки подключить, какие секреты передать.
- **Том (volume)** — хранилище, которое живёт отдельно от контейнера и не теряется при его пересоздании.
- **Bind mount** — подключение папки с настоящего компьютера внутрь контейнера.

Зачем: библиотека `better-sqlite3` собирается под конкретную систему, и на чужом компьютере установка часто падает. В образе она уже собрана, поэтому запуск не зависит от того, что установлено у пользователя.

## 3. Проверенные факты о проекте

Эти факты выяснены чтением кода. Именно на них построены решения ниже.

1. **Версия Node.** `better-sqlite3` версии 13.0.3 (зависимость сервера) требует **Node.js 22 и новее** (`engines.node >= 22`). В `README.md` сейчас написано «Node.js 18+». Это неверно, и README нужно исправить (раздел 9).
2. **Раскладка файлов.** `server/src/index.js` вычисляет корень проекта как `../..` от своего расположения и ищет фронтенд в `<корень>/web/dist`. Значит, в образе нужно сохранить раскладку `/app/server/src/...` и `/app/web/dist`.
3. **Файл конфига.** Сервер читает путь к конфигу из первого аргумента командной строки (`node server/src/index.js <путь>`), а без аргумента берёт `<корень>/config.json`. Это позволяет положить конфиг вне `/app`.
4. **Хост.** Адрес и порт берутся **только из конфига** (`host`, `port`). Переменных окружения для них нет. Значение `127.0.0.1` из `config.example.json` внутри контейнера не позволит достучаться до сервера снаружи. Нужен `0.0.0.0`.
5. **База CoreProtect** открывается так: `new Database(path, { readonly: true, fileMustExist: true })`, затем в `try/catch` выполняется `PRAGMA journal_mode = WAL` и `PRAGMA busy_timeout = 5000`. Если файла нет, сервер пишет ошибку и завершается с кодом 1.
6. **База авторизации.** `AuthStore` создаёт `data/auth.db` (путь берётся из `discordAuth.databasePath`, по умолчанию `data/auth.db`, относительно корня проекта) и включает в ней `journal_mode = WAL`. Каталог создаётся автоматически. Там лежат OAuth-состояния, **сессии и чёрный список**. Потеря файла означает, что все выйдут из системы и чёрный список обнулится.
7. **Секреты Discord** читаются только из переменных окружения `DISCORD_CLIENT_ID` и `DISCORD_CLIENT_SECRET`. Если `discordAuth.enabled: true`, а переменных нет, сервер не запускается (бросает ошибку при сборке приложения).
8. **Авторизация и маршруты.** При `discordAuth.enabled: true` все адреса `/api/*`, кроме `/api/auth/*` и `/api/admin/*`, без сессии возвращают `401`. Это важно для проверки состояния контейнера (раздел 6.5).
9. **Безопасность без авторизации.** При `discordAuth.enabled: false` API открыт всем и отдаёт `Access-Control-Allow-Origin: *`. Координаты и активность игроков доступны любому, кто доберётся до порта. Это прямо описано в README.
10. **Cookie.** Флаг `Secure` ставится только если `publicOrigin` начинается с `https://`. Для входа через Discord `publicOrigin` и `redirectUri` должны совпадать с адресом, по которому пользователь реально открывает сайт. Cookie состояния не передаётся между `localhost` и `127.0.0.1`.
11. **Корректное завершение.** В коде нет обработчика `SIGTERM`. Поэтому node в роли PID 1 в контейнере не остановится по `docker stop` сразу (нужен `init`, см. 6.4).
12. **Журналы** пишутся в stdout и stderr. Каждый HTTP-запрос даёт две строки, поэтому журнал растёт быстро.
13. **`cachePath` в конфиге не используется** (README: «залишено як спадок»). Папку и том под него создавать не надо.
14. **Bluemap.** Сервер сам ходит на `bluemap.baseUrl`. Если Bluemap запущен на том же компьютере, адрес `localhost` внутри контейнера указывает на сам контейнер, а не на компьютер пользователя.
15. `.gitignore` уже игнорирует `config.json`, `*.db`, `data/`, `node_modules/`, `web/dist/`, `.env`, `.env.*`, но разрешает `.env.example`.
16. Корневой `package.json` не использует workspaces. У `server/` и `web/` свои `package-lock.json`, поэтому `npm ci` работает в каждой папке отдельно.

## 5. Принятые решения (не менять)

### 5.1. Базовый образ

`node:22-bookworm-slim` (Debian, glibc). Не использовать `alpine`: нативный модуль на musl чаще приводит к проблемам.

### 5.2. Раскладка в образе

```
/app
├─ server/
│  ├─ package.json
│  ├─ node_modules/        (только production-зависимости)
│  └─ src/
├─ web/
│  └─ dist/                (собранный фронтенд)
└─ data/                   (пустой каталог для auth.db, принадлежит пользователю node)
```

Рабочий каталог: `/app`. Запуск: `node server/src/index.js /config/config.json`.

Корневой `package.json` и `package-lock.json` в образ не нужны.

### 5.3. Что монтируется снаружи

| Что | Куда | Как |
| --- | --- | --- |
| Каталог с `database.db` CoreProtect | `/coreprotect` | bind mount **каталога** (не файла), см. 7.1 |
| Конфиг | `/config/config.json` | bind mount файла, только чтение |
| Данные авторизации (`auth.db`) | `/app/data` | **именованный том**, не bind mount |

### 5.4. Что и как публикуется

Порт в `docker-compose.yml` публикуется только на локальный адрес хоста: `"127.0.0.1:${HOST_PORT:-3010}:3010"`. Выставлять порт на все интерфейсы (`3010:3010`) **нельзя**, потому что без Discord-авторизации API открыт всем (факт 9). Выход в интернет делает пользователь сам через reverse proxy, и это описывается в README.

### 5.5. Переменная для `Dockerfile` и Compose

Внутренний порт контейнера всегда `3010`. В `config.docker.example.json` `port` равен `3010`, а менять публичный порт нужно только через `HOST_PORT` в `.env`.

## 6. Dockerfile

### 6.1. Структура (три стадии)

1. **`web-build`** (база `node:22-bookworm-slim`):
   - скопировать `web/package.json` и `web/package-lock.json`, выполнить `npm ci`;
   - скопировать исходники `web/` и выполнить `npm run build` (внутри `tsc && vite build`);
   - результат: `/build/web/dist`.
2. **`server-deps`** (та же база):
   - скопировать `server/package.json` и `server/package-lock.json`, выполнить `npm ci --omit=dev`;
   - **проверить, что нативная библиотека реально загружается**: команда `node -e "import('better-sqlite3').then(m=>{const d=new m.default(':memory:');d.prepare('select 1').get();console.log('sqlite ok')})"` выполняется в этой же стадии, и сборка падает, если проверка не прошла (команду уточнить под ESM и рабочий каталог);
   - если `npm ci` не может скачать готовый бинарник и пытается собирать из исходников и падает без компилятора, установить в **этой стадии** (и только в ней) `python3 make g++` через `apt-get`, с очисткой кеша `apt` (`rm -rf /var/lib/apt/lists/*`). В итоговый образ эти пакеты попасть не должны. Если это понадобилось, указать в отчёте.
3. **`runtime`** (та же база):
   - `ENV NODE_ENV=production`;
   - `WORKDIR /app`;
   - скопировать `server/package.json`, `server/src`, `server/node_modules` (из `server-deps`) и `web/dist` (из `web-build`) с правами `--chown=node:node`;
   - создать `/app/data` и выдать владельца `node:node` (**до** смены пользователя, иначе том получит права `root` и `auth.db` не создастся);
   - `USER node`;
   - `EXPOSE 3010`;
   - `HEALTHCHECK` (6.5);
   - `CMD ["node", "server/src/index.js", "/config/config.json"]`.

Раскладку менять нельзя, иначе сервер не найдёт `web/dist` (факт 2).

### 6.2. Кеширование слоёв

Копировать `package.json` и `package-lock.json` **до** копирования исходников, чтобы зависимости не переустанавливались при каждой правке кода.

### 6.3. Что не должно попасть в образ

В `.dockerignore` (в корне) перечислить:

```
.git
**/node_modules
web/dist
data
*.db
*.db-*
*.sqlite*
config.json
config.docker.json
.env
.env.*
!.env.example
Product Requirements Document
*.md
!README.md
.vscode
.idea
**/*.log
```

Особенно важно исключить `**/node_modules`: модули, собранные на Windows или macOS, не работают внутри Linux-контейнера.

### 6.4. Завершение процесса

Так как в коде нет обработки `SIGTERM`, а node в роли PID 1 игнорирует сигналы остановки, в Compose обязательно указать **`init: true`** (лёгкий процесс-посредник tini передаёт сигналы). Без него `docker compose stop` будет ждать 10 секунд до принудительного завершения. Менять код для этого не нужно.

### 6.5. Проверка состояния (HEALTHCHECK)

**Нельзя** проверять `/api/config`: при включённой Discord-авторизации он вернёт `401` (факт 8), и контейнер будет вечно считаться нездоровым.

Использовать проверку, которая считает сервер живым, если он **отвечает кодом ниже 500** на `/api/auth/me` (при включённой авторизации ожидаемо `401`, при выключенной `200`):

```
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3010/api/auth/me').then(r=>process.exit(r.status<500?0:1),()=>process.exit(1))"
```

Перед использованием проверить команду в контейнере. Эта проверка подтверждает только, что процесс принимает соединения. Она **не** проверяет готовность базы (для этого нужен отдельный endpoint без авторизации, это предлагается в отчёте, раздел 11). В README написать об этом ограничении.

`start-period` не менее 20 секунд: при старте сервер синхронно читает справочники базы (миры, игроки, материалы), что на больших базах занимает время.

## 7. Работа с базой CoreProtect: самое важное

### 7.1. Монтировать каталог, а не файл

SQLite создаёт рядом с `database.db` служебные файлы (`-journal`, `-wal`, `-shm`). Если смонтировать только один файл, этих файлов внутри контейнера не будет, и чтение живой базы может не сработать или вернуть неполные данные. Поэтому монтируется **весь каталог**, где лежит `database.db`:

```
${COREPROTECT_DIR:?Укажите COREPROTECT_DIR в .env}:/coreprotect
```

А в конфиге контейнера: `"databasePath": "/coreprotect/database.db"`.

### 7.2. Режим только чтения

Приложение само открывает базу с `readonly: true`, поэтому записи в неё не будет. Дополнительная защита на уровне Docker (`:ro` на монтировании) желательна, но она может мешать SQLite (создание `-shm` файла в режиме WAL, откат «горячего» журнала). Поэтому действует правило:

1. По умолчанию в Compose монтировать **с `:ro`**.
2. Проверить оба режима журнала базы (раздел 10.4). Если на базе в режиме WAL чтение с `:ro` не работает, **убрать `:ro`** (приложение всё равно открывает базу только на чтение) и написать об этом в README и отчёте, объяснив причину.
3. Никогда не копировать базу в образ или в том, чтобы «обойти» проблему: данные должны быть живыми.

### 7.3. Права доступа

Контейнер работает от пользователя `node` (uid 1000). Файл базы принадлежит пользователю, под которым запущен Minecraft-сервер, и может быть недоступен для чтения (`600` или `640`). Тогда сервер завершится с ошибкой доступа. Нужно:

- описать эту проблему в разделе «Устранение неполадок» README;
- в Compose оставить закомментированную строку `# user: "1001:1001"` с пояснением, как подставить uid и gid владельца файла базы (команда `id` или `ls -n`);
- не запускать контейнер от `root` по умолчанию.

### 7.4. Где физически лежит база

Работать надёжно можно, только если `database.db` лежит на **локальном диске** того компьютера, где запущен Docker. Явно предупредить в README:

- сетевые файловые системы (NFS, SMB) и общие папки виртуальных машин **не поддерживаются**: блокировки SQLite на них ненадёжны;
- на Docker Desktop для Windows и macOS bind mount папок хоста работает через виртуальную прослойку, где блокировки и общая память SQLite могут работать нестабильно, а чтение медленнее. Для Windows надёжнее держать базу внутри файловой системы WSL2 (не на `C:\`);
- если Minecraft-сервер находится на другом компьютере, нужно отдельно настраивать регулярное копирование согласованного снимка базы. Это отдельная задача и вне этого задания.

## 8. Остальные файлы

### 8.1. `docker-compose.yml`

Один сервис `grieferfinder`. Не использовать устаревший ключ `version:`.

```yaml
services:
  grieferfinder:
    build: .
    image: grieferfinder:local
    init: true
    restart: unless-stopped
    ports:
      - "127.0.0.1:${HOST_PORT:-3010}:3010"
    environment:
      DISCORD_CLIENT_ID: ${DISCORD_CLIENT_ID:-}
      DISCORD_CLIENT_SECRET: ${DISCORD_CLIENT_SECRET:-}
    volumes:
      - ${COREPROTECT_DIR:?Укажите COREPROTECT_DIR в .env}:/coreprotect:ro
      - ./config.docker.json:/config/config.json:ro
      - grieferfinder-data:/app/data
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    # user: "1001:1001"   # если файл базы CoreProtect недоступен для чтения, см. README
    # extra_hosts:
    #   - "host.docker.internal:host-gateway"   # если Bluemap запущен на этом же компьютере

volumes:
  grieferfinder-data:
```

Требования:

- **Секреты** не записывать в файл. Только подстановка из `.env`.
- Имена и порядок можно уточнить, но свойства выше (`init`, привязка порта к `127.0.0.1`, том для `/app/data`, ротация журналов, обязательность `COREPROTECT_DIR`) обязательны.
- Настройки усиления защиты: `security_opt: ["no-new-privileges:true"]`, `cap_drop: [ALL]`, `read_only: true` вместе с `tmpfs: ["/tmp"]`. Включить их можно **только если** проверки раздела 10 проходят с ними. SQLite может использовать `/tmp` для временных файлов при тяжёлых запросах, поэтому `tmpfs` нужен, и запрос по большому диапазону времени надо проверить отдельно. Если какая-то настройка ломает работу, убрать её и записать в отчёт.

### 8.2. `.env.example`

```
# Каталог на этом компьютере, в котором лежит database.db плагина CoreProtect
COREPROTECT_DIR=/path/to/plugins/CoreProtect

# Порт на вашем компьютере (внутри контейнера всегда 3010)
HOST_PORT=3010

# Только если в config.docker.json включён discordAuth.enabled
DISCORD_CLIENT_ID=
DISCORD_CLIENT_SECRET=
```

Файл содержит только заглушки. Реальный `.env` в репозиторий не попадает (уже игнорируется).

### 8.3. `config.docker.example.json`

Копия `config.example.json`, где изменено только необходимое для контейнера:

- `"databasePath": "/coreprotect/database.db"`;
- `"host": "0.0.0.0"`;
- `"port": 3010`;
- `"discordAuth.databasePath": "data/auth.db"` (путь относительно `/app`, то есть том `/app/data`);
- `"discordAuth.enabled": false` по умолчанию, чтобы первый запуск работал без Discord (см. предупреждение ниже);
- реальные `guildId`, `adminRoleId` и `moderatorRoleIds` из `config.example.json` заменить заглушками вида `"000000000000000000"`, чтобы не тиражировать чужие идентификаторы;
- в `bluemap.baseUrl` оставить заглушку `https://bluemap.example.com`, а `bluemap.enabled` сделать `false`.

Остальные поля не менять. Поле `cachePath` убрать (оно не используется).

> ⚠️ При `discordAuth.enabled: false` API открыт любому, кто достучится до порта. Это допустимо **только** потому, что порт привязан к `127.0.0.1`. Нельзя открывать такой сервер наружу без включённой авторизации или защиты на уровне reverse proxy. Это предупреждение дословно повторить в README.

В `.gitignore` добавить строку `config.docker.json` (файл с настройками пользователя). Файл `config.docker.example.json` остаётся в репозитории.

## 9. Документация

В `README.md` (язык: украинский, как в остальном файле) добавить раздел «Запуск у Docker». Он должен содержать:

1. **Требования:** Docker Engine (или Docker Desktop) с Compose v2; расположение базы (раздел 7.4).

4. **Доступ из интернета:** порт привязан к `127.0.0.1`; для внешнего доступа использовать reverse proxy (Caddy, nginx) с HTTPS, а `publicOrigin` указывать как `https://...`. Только с включённой авторизацией.
5. **Bluemap на этом же компьютере:** использовать `host.docker.internal` и раскомментировать `extra_hosts`.
6. **Обновление версии:** `git pull`, затем `docker compose up -d --build`.
7. **Резервная копия:** том `grieferfinder-data` содержит сессии и чёрный список. Показать команду резервного копирования тома.
8. **Журналы:** `docker compose logs -f`.
9. **Ограничение проверки состояния** (6.5).
10. **Устранение неполадок:** (a) контейнер сразу завершается: нет файла конфига, неверный `databasePath`, нет `DISCORD_*`; (b) отказ в доступе к базе (7.3); (c) `SQLITE_CANTOPEN` или ошибки блокировки (7.2, 7.4); (d) страница недоступна: сервер слушает `127.0.0.1` внутри контейнера, поправить `host` на `0.0.0.0`; (e) `invalid oauth state`: открывать сайт именно по адресу из `publicOrigin`; (f) изменения конфига применяются только после `docker compose restart`, а если редактор заменил файл и контейнер видит старый, выполнить `docker compose up -d --force-recreate`.

## 10. Проверки и критерии приёмки

### 10.0. Если Docker недоступен агенту

Агент обязан выяснить это в самом начале (`docker version`). Если среда выполнения не содержит работающего Docker, то:

- выполнить только статические проверки: синтаксис Compose (`docker compose config`, если команда доступна), аккуратное чтение файлов и сверка с разделом 3;
- в отчёте **явно** перечислить все проверки из 10.1–10.5 как «НЕ ПРОВЕРЕНО»;
- не писать, что решение работает.

### 10.1. Сборка

1. `docker compose build` проходит с нуля (без кеша) и повторно (с кешем).
2. После правки только файла в `server/src/` пересборка **не** переустанавливает зависимости (слой с `npm ci` берётся из кеша).
3. В итоговом образе нет компилятора и `apt`-кешей из стадии `server-deps`, нет исходников `web/src`, нет `devDependencies` (проверить `ls`, размер образа, `npm ls --omit=dev` в `server`).

### 10.2. Отсутствие секретов в образе

Проверить внутри образа (`docker run --rm --entrypoint sh <образ> -c "ls -la /app; find / -name '*.db' -o -name 'config*.json' -o -name '.env*' 2>/dev/null"`): нет `config.json`, `config.docker.json`, `.env`, `*.db`. Проверить `docker history --no-trunc` на отсутствие значений секретов.

### 10.3. Запуск без авторизации

Подготовить **тестовую базу вне репозитория** (во временной папке, не коммитить) со схемой CoreProtect: таблицы `co_world`, `co_user`, `co_material_map`, `co_entity_map` и `co_block`, `co_container`, `co_item` (колонки как в `server/test/query-pipeline.test.js`) и несколькими строками. Затем:

1. Контейнер стартует и становится `healthy` не позже чем через 60 секунд.
2. `GET http://127.0.0.1:3010/api/meta` возвращает `200` и миры, игроков и материалы тестовой базы.
3. `GET /api/query?pageSize=10` возвращает события; `GET /` отдаёт `index.html` фронтенда.
4. Порт **недоступен** с других интерфейсов компьютера (проверить, что привязка только к `127.0.0.1`).
5. Контейнер работает от пользователя `node`, а не `root` (`docker compose exec grieferfinder id`).
6. `docker compose stop` завершает контейнер быстро (меньше 5 секунд), а не через 10 секунд.

### 10.4. Живая база (главная проверка)

Для **каждого** из режимов журнала тестовой базы, `journal_mode = DELETE` (по умолчанию) и `journal_mode = WAL`:

1. Запустить контейнер с монтированием каталога базы с `:ro`, затем без `:ro`.
2. Запустить на хосте процесс, который **пишет** в базу (добавляет события в `co_block` каждую секунду).
3. Пока он работает, несколько раз запросить `/api/query` и `/api/aggregate`. Ответы должны быть успешными, число событий растёт между запросами (после `POST /api/meta/refresh` если нужно обновить справочники; события читаются свежими без перезапуска).
4. Убедиться, что **файл базы не изменился записью со стороны контейнера** (хэш и время изменения файла не меняются из-за контейнера; допустимо появление или исчезновение `-shm` и `-wal` рядом в режиме WAL).
5. Записать результат для каждой комбинации в таблицу в отчёте: журнал (DELETE/WAL) × монтирование (`:ro`/rw) × работает ли чтение. Итоговые рекомендации в README (7.2) должны точно соответствовать этой таблице.

### 10.5. Авторизация и данные

1. С `discordAuth.enabled: true` без `DISCORD_CLIENT_ID` и `DISCORD_CLIENT_SECRET` контейнер завершается с понятным сообщением и не уходит в бесконечный перезапуск без объяснения (проверить журнал).
2. С заглушечными значениями секретов сервер стартует, `/api/auth/discord/start` отвечает редиректом на `discord.com`, а `/api/query` без сессии возвращает `401`. Контейнер при этом `healthy` (проверка из 6.5).
3. Именованный том работает: создать запись (например, пока нет Discord, достаточно убедиться, что файл `/app/data/auth.db` создался и принадлежит `node`), выполнить `docker compose down` и `up -d` (без `-v`): файл `auth.db` сохранился.
4. `docker compose down -v` удаляет том. Об этом предупредить в README рядом с резервной копией.

### 10.6. Общие критерии

1. Не изменены файлы приложения: `git diff --stat` не содержит `server/src/`, `web/src/`, `server/test/`, `web/test/`, `config.example.json`.
2. Тесты проекта проходят так же, как до работы: `cd server && npm test`, `cd web && npm test`.
3. В репозиторий не добавлены `config.docker.json`, `.env`, `*.db` и другие секреты и данные.
4. Все файлы раздела 4 существуют, а `README.md` обновлён по разделу 9.
5. Любое отклонение от решений разделов 5–7 описано в отчёте с причиной.
